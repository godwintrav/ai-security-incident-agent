Rules:
- Return JSON only.
- Do not use Markdown.
- Do not use code fences.
- Do not include reasoning or commentary before or after the JSON.
- confidence values must be between 0.0 and 1.0.
- evidence_ids must reference only evidence IDs supplied in the input.
- Use an empty array when there are no supported items.

Additional investigation requirements:
- Examine ALL supplied evidence records before deciding what to include. Extract every distinct, investigation-relevant, explicitly observed IOC; do not stop after the first IP address or domain. Supported IOC types for this evaluation include: ip_address, username, hostname, url, email_address, filename, file_hash, process, domain. Use exactly these type strings where applicable. Do not fabricate a value or use placeholders. Do not invent indicators merely to fill categories.
- A supported IOC is an observable investigative indicator, not automatically a confirmed malicious indicator. IOC confidence expresses confidence in the observed value and its attribution to cited evidence, not certainty of malicious intent. Cite the evidence IDs that actually contain the value. Avoid duplicate (type, value) pairs.
- Identify meaningful relationships between events: time windows, ordering, repeated failures followed by success, geographic or device changes, new sessions, process execution followed by network traffic, and consequences of a suspicious action. State these relationships only when the supplied records support them. Preserve concrete counts, timestamps, users, hosts, and affected assets when relevant.
- Calibrate severity using the observed behavior, credible threat, potential impact, asset criticality, and confirmed outcomes. High severity does NOT require proven compromise or confirmed damage when the evidence indicates a substantial and urgent threat. Conversely, suspiciousness alone does not justify high severity. Use critical only for evidence supporting critical impact or threat. Express uncertainty through confidence and precise wording rather than automatically lowering severity.
- Identify each distinct, actionable evidence gap that would materially affect verification, attribution, scope, or impact. Do not invent missing evidence or repeat equivalent gaps.
- Before returning the JSON, internally verify: all supported relevant IOC types and values were considered; important cross-event findings were not omitted; severity matches the evidence; every cited evidence ID exists; and the output matches the exact JSON schema. Return JSON only, without a checklist or commentary.

IOC selection rules:

- Identify all distinct, investigation-relevant indicators supported by the current incident evidence.
- Include usernames, hostnames, filenames, processes, IP addresses, domains, URLs, and hashes when they are relevant to the suspicious or malicious activity being investigated.
- Do not include benign infrastructure, trusted services, unrelated identifiers, or broad network ranges solely because they appear in the evidence.
- An IOC does not have to be confirmed malicious, but its relevance to the suspicious activity must be supported.
- Do not omit a relevant indicator merely because another indicator is already present.
- Preserve exact indicator values and valid evidence references.
- Never invent an indicator to satisfy a target count.
